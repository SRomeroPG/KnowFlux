# SG-0003 — Colliding provisional ID ordering and alias identity

## Discovered in

Phase: P002 ID Registry
Team: Codex
Agent: Implementation Lead, independently checked by spec-analyst

## Relevant spec sections

Core Specification v2.1 §8.2 (collision, `first_canonical_commit`, and indefinite `id_alias` resolution), §19.1 (canonical first appearance and squash merges), §10.7 (unqualified entity addresses), and §42.2 (`KF-E-101`).

## Missing semantic decision

Two provisional records can carry the same ID on different branches and enter the canonical branch together in one merge or squash commit. Both then have the same `first_canonical_commit`; the rule to renumber the one with the later commit does not choose a record. When commits differ, renumbering one record still leaves the old ID assigned to the survivor. An unqualified query for that old ID cannot both identify the survivor and resolve the renumbered record's `id_alias` in all queries indefinitely. The spec does not define a source-qualified alias identity, query disambiguation, or precedence rule.

## Why implementation cannot proceed safely

Choosing an order for equal commits changes which entity receives a permanent ID. Choosing alias precedence changes what an existing unqualified ID means. Both alter persistent identity and can silently route queries to the wrong entity. A registry schema and reference-rewrite rule for this collision cannot be selected as an implementation detail.

## Concrete alternatives discovered

- Define a stable tie-breaker for records entering in the same canonical commit, and make aliases source-qualified (for example by stable entity identity or originating branch/commit) with a query syntax that preserves unqualified access to the surviving ID.
- Reject simultaneous-entry collisions for manual resolution, and define which queries can resolve a historical alias while the old ID remains live.
- Assign distinct IDs to colliding provisionals before either reaches the canonical branch, with an explicit rule for references and historical aliases.

These are alternatives only; this artifact does not choose one.

## Affected workstreams

P002 automatic provisional/provisional merge-collision resolution and indefinite alias resolution for such collisions; any P002 completion or Claude-ready handoff that asserts those requirements. Later general query and reference-resolution phases also depend on the decision.

## Unaffected work that may continue

Engine-only allocation under a transactional lock, non-reuse and prefix formatting, provisional creation off canonical, canonical promotion when IDs do not collide, and detection of permanent collisions with `KF-E-101`.

## Required decision authority

User or future frozen-spec revision.
