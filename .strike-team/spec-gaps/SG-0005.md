# SG-0005 — Canonical branch source for the Knowledge Repository

## Discovered in

Phase: P002 ID Registry
Team: Codex
Agent: spec-analyst and Implementation Lead

## Relevant spec sections

Core Specification v2.1 §3.2 (`workspace.yaml`), §8.2 (canonical promotion), §19.1 (transaction time on the Knowledge Repository canonical branch), and §50 (`kf.yaml` configuration example).

## Missing semantic decision

The spec requires `kf validate` to promote provisional IDs when they enter the Knowledge Repository's `canonical_branch`, but it does not declare where that branch is configured or how the engine discovers it. `workspace.yaml` gives `canonical_branch` only for registered source repositories, while `knowledge` declares only a path. The §50 `kf.yaml` example has `ids.padding` but no Knowledge Repository branch setting.

## Why implementation cannot proceed safely

Hardcoding `main`, reading a remote default branch, or borrowing one of the source-repository settings can promote on the wrong branch. That makes an ID permanently immutable before canonical publication. A P002 API could accept a caller-provided branch, but the required `kf validate` behavior needs an authoritative project-level source.

## Concrete alternatives discovered

- Add an explicit `knowledge.canonical_branch` field to `workspace.yaml`.
- Add a Knowledge Repository canonical-branch setting to `kf.yaml`.
- Define a precise Git-based discovery rule and failure behavior when the result is absent or ambiguous.

These are alternatives only; this artifact does not choose one.

## Affected workstreams

P002 automatic promotion and P007 `kf validate` integration; P016 transaction-time derivation also needs the same branch identity.

## Unaffected work that may continue

Registry initialization and provisional allocation with transactional locking, ID formatting and non-reuse within a retained registry, and conservative collision detection.

## Required decision authority

User or future frozen-spec revision.
