# SG-0002 — Address grammar for observed targets and scope values

## Discovered in
Phase: P001 (Claude audit R01, `CLAUDE_AUDIT_R01.md`); affected implementation is later reference resolution and addressing
Team: Claude
Agent: Claude Audit Orchestrator, from candidate reports by spec-compliance-auditor, architecture-auditor and test-conformance-auditor

## Relevant spec sections
Core Specification v2.1 §3.2 (last paragraph), §10.4, §10.6, §10.7, §22 (`affects` example), §40 (`facets[].key`), §50 (`facets.observed_target_dimensions`).

## Missing semantic decision
The frozen text defines two keying schemes and one address grammar, and they do not cover each other:

1. **Observed target dimensions vs. address grammar.** §10.6: "**Faceta observed** — clave `target`, mapa abierto". §50 makes the dimensions configurable: `observed_target_dimensions: [repository, environment]`. §10.7 defines observed addresses only as `BR-0037#observed:legacy-app` ("por repositorio") and `BR-0037#observed:legacy-app/production` ("con entorno"). The spec does not say (a) whether `target.repository` is mandatory, (b) how a target that has additional or different configured dimensions, or an observation-scope `target.scope`, is addressed, or (c) how two observed facets with the same repository/environment and different additional dimensions (legal per §10.6 "mapa abierto" and KF-E-212) are distinguished in an address.
2. **Field suffix vs. target identifier.** §10.7 uses `.` both inside the grammar (`DE-0017#observed:legacy-app.concentration`, "campo en una faceta") and possibly inside repository identifiers. §3.2 places no character restriction on `repositories[].id`. A repository id containing `.` makes `X#observed:a.b` ambiguous between repository `a.b` and repository `a` + field `b`.
3. **Scope values in `canonical(scope)` and `[k=v]` addresses.** §10.6: "pares clave=valor ordenados lexicográficamente, valores de lista ordenados, separados por ";"". §22 writes a two-value list as `[business_unit=A;business_unit=B]`. The spec defines no escaping or character domain for scope keys and values, so values containing `;`, `=`, `]`, `.`, whitespace or non-ASCII characters produce ambiguous or unparseable `specified_key`s and scope addresses. It also does not say how non-string scalar values (numbers, booleans) are rendered in `canonical(scope)`.

## Why implementation cannot proceed safely
Any parser, `specified_key`/`observed_key` canonicalizer, or `div_key` (§23.2, which hashes `specified_key` and `observed_target`) would have to choose a character domain, an escaping rule, and a target-to-address mapping. Each choice changes which persisted YAML is addressable and which keys collide, so it is a persistent-format decision, not an implementation detail. The P001 schemas currently accept the whole open domain, which makes nothing impossible but also resolves nothing.

## Concrete alternatives discovered
- Restrict identifiers (repository/environment ids, scope keys and values) to a character class that excludes the grammar's delimiters, and make `target.repository` mandatory. Additional target dimensions would then be non-addressable, or require a grammar extension.
- Keep the open domain and define an escaping/quoting rule for address segments and `canonical(scope)`, plus an address form for arbitrary configured target dimensions (for example, a `[k=v;…]` selector after `observed`).
- Keep the grammar as is and declare that facets whose target or scope cannot be expressed in §10.7 syntax are addressable only by a derived canonical key form (as in §40 `facets[].key`).
