# SG-0004 — Proving identity continuity before permanent promotion

## Discovered in

Phase: P002 ID Registry, independent integration review
Team: Codex
Agent: integration-engineer; independently verified by Implementation Lead

## Relevant spec sections

Core Specification v2.1 §8 (unique, non-reusable, name-independent IDs), §8.1 (engine registry and transactional lock), §8.2 (permanent IDs never renumber), §9.1 (operational append-only registry), and §19.1 (first canonical appearance).

## Missing semantic decision

The spec does not define an immutable entity-incarnation marker or another way to bind a registry allocation to the same entity across deletion, recreation, rename, move, and canonical history. The only persistent entity identifier is the ID whose ownership must be proved. `id_status` and entity identity fields are mutable, and the registry format is unspecified.

## Why implementation cannot proceed safely

An implementation that records only ID and status can allocate `BR-0001` to entity A, promote A, then accept a different committed entity B with `BR-0001` after A is deleted. The ID is reused while the registry appears valid. A path-only binding would reject legitimate moves and still cannot distinguish a delete/recreate at the same path. A content or name binding would violate name independence and legitimate edits. Automatically promoting without a continuity rule can silently convert a stolen permanent ID into accepted identity.

## Concrete alternatives discovered

- Define a persistent immutable incarnation token in each entity and the registry, with rules for moves, merges, and migration of existing v2.1 entities.
- Define Git-history-based continuity and the exact behavior for squash merge, rename, delete/recreate at the same path, and history rewrite detection.
- Require an explicit engine-managed ownership proof or manual review for promotion, with a specified registry record and query behavior.

These are alternatives only; this artifact does not choose one.

## Affected workstreams

P002 automatic promotion to `permanent`, reliable non-reuse across entity deletion/recreation, and complete permanent-collision handling. P007 `kf validate` promotion integration and later Git history/revision workflows also depend on this decision.

## Unaffected work that may continue

Fresh-project engine allocation under a transactional lock, provisional status, monotone prefix sequences, refusal to reissue IDs recorded in the registry, and conservative duplicate-ID detection. SG-0003 separately blocks automatic provisional-collision renumbering and aliases.

## Required decision authority

User or future frozen-spec revision.
