P001 NORMATIVE SCOPE
────────────────────────────────────────────────────────

P001 implements the first bounded portion of §53 Phase A:

    Repository Foundation + Core Persistent Model

Its principal normative responsibility is:

    JSON Schemas for the 11 core types with facets,
    schema_version: 2.1.

P001 may contain only the minimal scaffolding needed to build and verify that
persistent contract.

Audit whether it accidentally implements later semantics incompletely or
creates architecture that will conflict with subsequent §53 phases.

────────────────────────────────────────────────────────
MANDATORY AUDIT FOCUS
────────────────────────────────────────────────────────

Audit at minimum all of the following.

CORE TYPES

Verify all 11 core types are represented correctly:

- Capability
- BusinessProcess
- BusinessRule
- DataEntity
- Outcome
- Scenario
- Evidence
- Unknown
- Change
- Divergence
- Dispute

FACETING

Verify exactly the intended core types are faceted:

- BusinessProcess
- BusinessRule
- DataEntity

Verify these are NOT facetable:

- Capability
- Outcome
- Scenario
- Evidence
- Unknown
- Change
- Divergence
- Dispute

Verify:

- identity is separate from facets;
- specified semantics are represented correctly;
- observed semantics are represented correctly;
- greenfield usage does not require unnecessary observed-facet ceremony;
- obsolete v2.0 truth_state semantics do not remain.

MULTIPLICITY / ADDRESSING

Verify the persistent representation can support:

- specified facet multiplicity by scope + validity window;
- observed facets by target;
- target repository/environment dimensions;
- future addressing semantics without forcing a migration.

Do not require P001 to implement later CLI resolution unless explicitly in
scope, but the data model must not make the normative addressing model
impossible.

RELATIONSHIP OWNERSHIP

Verify canonical authored relationship ownership.

Especially verify that derived inverses cannot be silently authored where
the schema can deterministically prevent it.

Look aggressively for accidental support for:

- executed_by
- supported_by
- exercised_by
- governed_by
- produced_by
- read_by
- written_by
- called_by
- overridden_by
- blocked_by
- affected_by
- is_disputed

in authored locations where v2.1 forbids them.

FACET REFERENCES

Verify the persistent contracts correctly represent the intended reference
direction for:

- EV.supports → facet for faceted entities;
- SC.asserts → specified/observed target;
- CHG.affects → specified facet;
- DSP.disputes → entity or facet.

Do not invent runtime resolution behavior not required by P001.

AUTHORED VS DERIVED

Verify the schema/contracts do not accidentally turn derived values into
independent authored truth.

Inspect especially:

- version;
- computed_confidence;
- effective_confidence;
- canonical signature value;
- verification-derived fields;
- evidence hint_lines;
- inverse relationships;
- created_at;
- updated_at.

If P001 temporarily represents any derived field for fixture reasons, verify
that the representation cannot be confused with user authority and that this
is actually permitted by the frozen spec.

SCHEMA COMPOSITION

Look for loopholes created by:

- permissive additionalProperties;
- ambiguous oneOf / anyOf;
- schema inheritance;
- union widening;
- nullable fields;
- weak references;
- missing enum boundaries;
- duplicated definitions;
- circular composition;
- inconsistent required fields;
- schemas that accept impossible combinations.

A schema is not correct merely because the positive examples validate.
