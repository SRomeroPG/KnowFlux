STEP 3 — DEFINE P001
────────────────────────────────────────────────────────

P001 SHALL cover:

    "Repository Foundation + Core Persistent Model"

Its principal normative objective is §53 Phase A, item 1:

    JSON Schemas for the 11 core types with facets,
    schema_version: 2.1.

It MAY include only the minimum repository/tooling scaffolding required to
make those schemas buildable and testable.

It SHALL NOT pull forward substantive implementations of:

- ID allocation;
- EvidenceResolver;
- confidence computation;
- full kf validate;
- logic evaluator;
- graph construction;
- change ledger;
- DIV derivation;
- work-item refinement;
- portal;
- chatbot;
- provider integrations;

except for minimal interfaces/placeholders strictly required to establish a
clean architecture.

A placeholder SHALL NOT pretend to implement a future normative feature.

P001 must establish the persistent data contract correctly, because later
phases depend on it and schema migration is expensive.

Pay special attention to v2.1's facet model:

- faceted core types:
  - BusinessProcess
  - BusinessRule
  - DataEntity

- non-faceted core types:
  - Capability
  - Outcome
  - Scenario
  - Evidence
  - Unknown
  - Change
  - Divergence
  - Dispute

Remember:

- identity is not a facet;
- specified and observed have different multiplicity/key semantics;
- inverse relationships are derived and forbidden in authored YAML;
- evidence supports facets for faceted entities;
- CHG affects specified facets;
- SC asserts the correct facet;
- derived fields must not become independently authored truth;
- the simple greenfield case must remain usable without exposing unnecessary
  facet ceremony.

Do not simplify the model merely because implementation is easier.
